# MieGO UX原則

状態: **Draft／未確定**。作成日: 2026-10-19。対象: MieGO（9・13・19路盤）の現行Web UI。

この文書は**なぜそうするか**（原則と、決めたことの理由）を書く。何がどこにあり、値がいくつかは [`UX_SPEC.md`](UX_SPEC.md)（以下「仕様」）に書く。仕様を変えるときに原則と食い違うなら、先にこの文書を直す。

## 1. 目的と原則

- **スマートフォン縦画面を第一対象**とする。碁盤を主役にし、着手に必要な可視領域をできる限り確保する。
- **スマートフォン横画面への最適化は対応不要**。横向き専用レイアウト、横向きを促すUIは設計しない。
- 操作・情報・装飾を増やす前に、既存の表示枠の再利用、状態による切り替え、省略を検討する。
- **無用なカード表示で線を増やさない**。まとまりは余白と文字の大きさで示し、枠線・背景・区切り線は付けない。碁盤の下は碁盤の枠、アゲハマの枠、ボタンの枠が並ぶので、そこにカードの枠を足すと線が重なって見える（例：採点の得点欄は枠なし）。
- 通常の着手・終局提案・パス・投了・採点への同意はそれぞれ異なる行為として扱う。
- 形勢・地合いの推定は確定情報ではない。死石候補は利用者が訂正・確認できるようにする。
- 対局の途中で状態が変わっても、操作位置と情報の意味をできるだけ安定させる。
- **画面の枠はダークだけ**（`color-scheme: dark`。決定：枠のライト版は作らない）。明るさを変えるのは碁盤の見た目（木目／ライト／ダーク／カスタム）だけにする。理由は §2.1。

## 2. 決めたことと理由

### 2.1 画面の枠はダークだけ

理由は3つ。

1. 碁盤を画面でいちばん明るい面にして主役にするため。枠が明るいと、木目やライトの盤が枠に溶ける。
2. 地合いの色は碁盤ごとに黒側と白側が同じくらい目立つよう調整しており（仕様 §2.4「碁盤の見た目」）、その周りの枠を1通りに固定すると、色の確認が盤の種類の数だけで済む。
3. 夜や暗い部屋で長く打つことが多い対局アプリで、まぶしさを抑えるため。

- 反対の見解：Apple HIG（Dark Mode）は、明暗どちらの外観でも見やすくし、アプリ独自の外観設定は避けるよう勧めている。それでも上の理由を優先して、ダークだけにすると決めた。色はトークン（仕様 §7）から取るので、将来見直すときも `:root` の値を差し替えれば済む。

### 2.2 着手はいつも2タップ

着手はどの盤・どのモードでも「仮置き→ここに打つ」の2タップで、1タップで打つ設定は置かない（決定。配置は仕様 §2.5「着手操作」）。

- 理由は誤タップを防ぐため。特に13・19路は、320px の19路で1路が約14pxしかなく、押し間違えた手を確定前に直せることが要る。
- OGS はライブ対局を既定で1クリックにし、通信対局では確定ボタンを出し、設定で選べるようにしている。Chess.com の「Confirm Each Move」は利用者が選んだときだけ使う。
- MieGO は盤の大きさや利用者で操作を変えず、どこでも同じ2タップにそろえる。9路の対COMでは商業アプリより1手ごとのタップが多いが、それは受け入れる。

### 2.3 対局画面はカードで囲まず、ボタンの縁は残す

- 対局画面（ヘッダーと盤の下）では、まとまりをパネルやカードで囲まず、余白で分ける（線が要る面をそもそも作らない。§1「無用なカード表示で線を増やさない」）。
- ただしボタンの縁は残す：暗い塗りだけでは背景に溶けてボタンと分からないため。
- 融合したボタンは外側も境目も同じ色の線にする：境目を暗い隙間にすると、暗い塗りの間で区切りが見えないため。
- 金の縁（主操作・強調枠）は意味があるので残す。

値と描き方は仕様 §3.1・§3.6。

### 2.4 操作は動詞、行き先と状態は名詞

- 囲碁の行為として名前が定着している操作は、その名詞のまま使う（「パス」「投了」「待った」「もう一局」）。動詞にすると（「パスする」）かえって読みにくい。
- Apple HIG も、ボタンには短い具体的な動詞を勧めつつ、ナビゲーションの行き先には名詞を使っている。

規則は仕様 §3.3。

### 2.5 ブラウザの確認ダイアログは使わない

ブラウザの確認ダイアログ（`confirm()`・`alert()`）は使わない。見た目と操作がアプリの他の部分と揃わず、読まずにOKを押す癖もつきやすいため。代わりの手順は仕様 §3.4。

### 2.6 最小寸法の根拠

値は仕様 §5。

- 押せるもの 44×44px：Apple HIG の最小 44pt。WCAG 2.2 の 2.5.8（24px）は下限で、目標ではない。
- 盤の交点だけは例外：19路の320px では1路が約14pxになるので、仮置き→「ここに打つ」の2段で誤タップを防ぐ（§2.2）。
- 文字 11px：Apple HIG の iOS の最小 11pt。

### 2.7 今の対局を変える入口と、次の対局を決める入口を分ける

- 「新規対戦」シートは次の対局だけを決める。今の対局の打ち手（人かCOMか、COMのキャラ）は、盤の下の対局者の名前から開く「この対局の打ち手」で替える（仕様 §2.22）。
- 理由：同じシートに今の対局に効く設定と次の対局に効く設定が混ざると、押す前にどちらに効くか分からない。替えたい相手の名前そのものを押す方が、手数も少なく迷わない。
- 1台・対COM・観戦は、黒と白の打ち手の組み合わせとして扱う。モードを替えても棋譜は続き、観戦の「介入する」も同じ規則（手番の色を人にする）で説明できる。
- 盤・ルール・置き石・持ち時間のように盤そのものが変わるものは、今の対局では替えず、新しい対局（新規対戦・「ここから打つ」）にする。
- 反対の見解：Lichess・Chess.com・OGS は、局面から打ち直すときは別の対局として記録を分けている（OGS は分岐した対局を段級位に数えない）。MieGO には段級位がないので、1つの棋譜の途中で打ち手が替わることを受け入れる。Chess.com も、始めた練習対局の中ではボットと手番をその場で替えさせている。

## 3. 未決の検討事項

1. **スクロール規則**: 碁盤が大きい端末で、採点詳細と固定操作列が重ならない位置を決める。
2. **COM不在時の手動採点**: KataGoがいつまでも読み込めない場合、どの既存操作で明示的に手動採点へ進むか。
3. **ネット切断・再接続**: 状態、再試行可否、招待URLの利用可能性をどこまで表示するか。
4. **履歴と再戦の区別**: 既存対局の再開、新規対局、設定変更を混同させない文言・確認手順。
5. **アクセシビリティ**: フォーカス移動、Canvasの代替操作（最小寸法は仕様 §5 で決めた）。
6. **初回学習**: 終局の提案とパスの違い、コウ・自殺手、死石の修正はヘルプシートで説明する。初回起動時に自動で案内するかは未決。
7. **通信競合時の整合性**: 双方が同時に死石修正した場合の最終確認と、盤面が食い違ったときの回復方法。

この草案は、未決の項目について関係者が合意した後に正式版とする。
